# Benchmarks

Numbers in this file are measured, not estimated. Every row records the machine
class, the payload and the exact commands, so anyone can re-run it and see the
same order of magnitude.

> **Read the labels.** The M1 numbers below are **loopback on one Windows
> machine**. They say the pipeline works and roughly how much it costs; they are
> not a claim about real LAN throughput.

---

## M1: single-file upload, loopback

**Date:** 2026-11-08
**Build:** release (`cargo build --release -p flit-cli`), `flit 0.1.0`
**Machine:** Windows 11, x86_64, local NTFS volume
**Link:** loopback (`127.0.0.1`) — no NIC, no switch, no Wi-Fi in the path
**Payload:** zero-filled file created with `File.SetLength` (the bytes are real;
nothing in the pipeline knows they are zeros)

### Procedure

```sh
# once, to learn the fingerprint a peer would pin
flit identity --identity ./id.key

# receiver
flit serve --identity ./id.key --bind 127.0.0.1 --port 47821 --dir ./recv

# sender, three times
flit send payload.bin --to 127.0.0.1:47821 --fingerprint <fingerprint>
```

`flit send` prints the elapsed time around the whole operation and the MiB/s
derived from it. That figure **includes hashing the source file once** before the
manifest is sent, which is the honest number for what a user waits.

### Results

| Payload | Run | Wall clock | MiB/s | Verified |
|---|---|---|---|---|
| 1 GiB | 1 | 7.35 s | 139.3 | yes |
| 1 GiB | 2 | 7.59 s | 134.9 | yes |
| 1 GiB | 3 | 9.35 s | 109.6 | yes |
| 64 MiB | 1 | 0.32 s | 201.1 | yes |
| 64 MiB | 2 | 0.38 s | 170.5 | yes |
| 64 MiB | 3 | 0.37 s | 171.5 | yes |

After all six transfers the receive directory contained every file at its exact
declared length, and `.flit/parts` was empty: no abandoned parts, no orphans.

### Context

Same machine, same disk, for scale:

| Operation | Time for 1 GiB | Rate |
|---|---|---|
| `Copy-Item` (raw file copy) | 0.89 s | 1,149 MiB/s |
| `Get-FileHash -Algorithm SHA256` | 2.87 s | ~357 MiB/s (PowerShell) |
| `flit send`, end to end | 7.35 s | 139 MiB/s |

### What this does and does not tell us

It tells us the pipeline is correct at scale: 1 GiB streams through TLS 1.3,
hashes on the way in, verifies at finish, and installs under its real name
without holding the file in memory.

It also tells us the pipeline is roughly **8× slower than a raw copy on the same
disk**, which is the first real performance finding for this project. Two
candidate causes, neither yet isolated:

1. Received bytes were written with blocking `std::fs` calls inside the async
   handler, so the TLS read and the disk write never overlapped. **Addressed:**
   the receiver now opens the `.part` file through `tokio::fs` and writes
   through a 1 MiB `BufWriter`, which moves the blocking work to Tokio's
   blocking pool and coalesces the small TLS frames into disk-sized writes.
   The numbers above predate that change; they need re-measuring on the same
   machine before the gap is called fixed.
2. The receiver writes into `.part` while Windows Defender has real-time
   scanning enabled, and Smart App Control is on for this machine. Scanning a
   file that grows 1 GiB is a plausible large tax that would not appear on a
   Linux receiver.

Note that the sender already hashes the file before the transfer, so some of the
gap is unavoidable: the same bytes are processed twice on the sending side. The
`Copy-Item` comparison is a lower bound, not a target.

### Things that were tried and rejected

| Change | Result |
|---|---|
| Raise the client's read chunk from 256 KiB to 1 MiB | **Slower** — 87–94 MiB/s on the same 1 GiB payload |

So per-frame overhead is not the bottleneck, and 256 KiB frames stay.
